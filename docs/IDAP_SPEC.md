# IDAP: Intent-Driven Adaptive Precision (意图驱动自适应精确度协议规范)

**版本**: 1.0.0-Draft  
**状态**: 核心协议规范  

---

## 1. 概述

Tars 是一个高效、理性、且具备极强执行力的 AI 助手。为了在多样化的现实任务中最大化效率并避免在低容错任务中产生幻觉，Tars 引入了 **意图驱动自适应精确度协议 (IDAP)**。

IDAP 旨在通过对用户意图进行**分级识别**，动态调整子任务的**执行深度**与**审计判定严苛度**，从而在“极速高可行性规划（如自驾游大纲）”与“100%零误差严格执行（如代码编写与金融交易）”之间取得极致的理性平衡。

---

## 2. Tars 六级精确度光谱 (The 6-Level Precision Spectrum)

IDAP 定义了六个分级的精确度区间，分为三个大象限：

```
【非事实创意象限】                    【混合决策象限】                  【物理执行象限】
 L1 (概念探索) -> L2 (宏观规划)  -->  L3 (可行指南) -> L4 (调研分析)  -->  L5 (高保事实) -> L6 (严格事务)
```

### 2.1 第一象限：非事实创意象限（Creative & Brainstorming）

#### L1: `EXPLORATORY_CONCEPT` (概念探索级)
*   **适用场景**：发散脑暴、故事大纲设计、宽泛的系统架构设想。
*   **执行要求**：最大化发散思维，**0 事实性核验**。
*   **审计标准**：宽松通过。禁止 Auditor 以任何缺失数据、缺乏细节等事实性理由驳回。

#### L2: `MACRO_PLANNING` (宏观规划级)
*   **适用场景**：长期战略路线图、粗线条概算（例如：“来回行程半个月左右，预算四五千”）。
*   **执行要求**：确保全局宏观逻辑自洽，**不需要**任何具体实体（如具体酒店名、餐馆门牌号、实时班次）的定位。
*   **审计标准**：审查大方向的可行性。只要宏观逻辑完整，直接通过。

---

### 2.2 第二象限：混合决策象限（Hybrid & Decision Making）

#### L3: `FEASIBLE_PRACTICAL` (可行指导级)
*   **适用场景**：**默认通用指南级**（如常规自驾游规划、非核心系统日常维护流程指引）。
*   **执行要求**：推荐的实体（如酒店、停靠地）**必须真实存在**（提供真实OTA链接），但微观细碎数据（如前台联系电话、实时客房价格波动、小镇医院座机等）允许使用“当天实时导航获取”作为合理对策，无需在规划阶段进行深度网络爬取。
*   **审计标准**：审查框架真实性与逻辑可行性。允许合理估计（如油耗估计、正常房费区间），允许合理提示占位符。

#### L4: `RESEARCH_ANALYTICAL` (调研分析级)
*   **适用场景**：严肃行业调研、多平台竞品比价、高风险天气与交通预警。
*   **执行要求**：**引用的核心数据必须具备时效性并提供真实参考数值**，不允许以“当天自查”为由留空。必须明确标注参考来源 (`data_source`) 与抓取时间戳 (`data_timestamp`)。
*   **审计标准**：审查数据是否真实反映近日报道/API 情况。允许合理的测量误差公差。

---

### 2.3 第三象限：物理事实型象限（Factual & Transactional）

#### L5: `FACTUAL_VERIFIED` (高保真事实核验级)
*   **适用场景**：学术论文引用、紧急救援与就医名录、高风险特种自驾求生指南。
*   **执行要求**：**确保 100% 绝对精确事实**。所有地址、电话、路况气象警报必须真实且通过搜索引擎/API 多方确认。严禁使用“大概”、“左右”等估计性描述。
*   **审计标准**：极致核验。任何关键事实缺失或存在估计性语言，直接予以驳回。

#### L6: `STRICT_TRANSACTIONAL` (严格事务级)
*   **适用场景**：代码运行与修复、数据库读写、系统命令执行、资产划转。
*   **执行要求**：**零容错**。结果必须成功通过单元测试或取得 100% 安全的终端回执。
*   **审计标准**：硬核校验。任何微小的语法错误、不匹配或警告直接打回 Executor 重写，直到通过为止。

## 3. 步骤级意图 (Step-Level Intent) 与显式干预 (User Overrides)

IDAP 具备微观的灵活性与主动感知性：

### 3.1 步骤级意图解析
在 **Planner** 阶段，PM 会将用户的整体 Goal 拆解为多个 SubTask。
*   每一个 SubTask 都会被 PM 赋予一个 `L1` 到 `L6` 的标签（例如：`1. 规划上海至成都的行驶里程路线 (L2)`）。
*   下游的 Executor 与 Auditor 在读取 SubTask 时，会自动针对当前 SubTask 标签执行对应的工具调用力度与审计判定阈值。
*   **优势**：使 Tars 能完美胜任混合任务（例如：大部分自驾路线采用 `L3`，而最后一步将路线用 Python 存入 JSON 的步骤自动升级为 `L6`）。

### 3.2 显式约束干预 (User Overrides)
如果用户的输入中包含**显式强事实词汇**（如：“*必须包含每天酒店的真实前台座机以确认带宠物*”、“*需要极精确的实时油耗，不能有估计*”）：
*   **Planner** 的 NLP 提取器会在子任务分发前触发“显式升级机制”，将原本属于 `L3: FEASIBLE_PRACTICAL` 的常规子步骤强制升级为 `L5: FACTUAL_VERIFIED`。
*   系统将据此拉高执行与审计标准。

## 4. LangGraph 逻辑集成

1.  **数据沉淀**：意图级别与子任务列表绑定，记录在 `SubTask` 对象的 `precision_level` 字段中。
2.  **Executor 执行**：`think_node` 拼接 System Message 时，自动将当前子任务的 `precision_level` 解包，并向 Executor 声明具体的执行标准。
3.  **Auditor 审查**：`auditor_node` 在构建人机审查提示时，提取各步骤对应的 `precision_level`，引导大模型按标准进行 Approved/Rejected 审查。

## 5. IDAP Phase 2: 进阶执行与安全隔离协议

为了应对多智能体长流程任务中容易出现的“步骤碎片化”、“高频重复搜索”、“模拟占位调用”以及“根目录文件乱写”等系统级执行痛点，IDAP 协议在 Phase 2 引入了以下高阶执行规范与物理防护屏障：

### 5.1 动态计划密度 (Adaptive Subtask Density)
*   **规范机制**：Planner 必须根据用户指令的详略程度、复杂度和显式限制词（如“简单点即可”、“粗略攻略”或“极其详尽”）自适应调控生成的子任务总数：
    - **极简/快速任务**：压缩并合并同类步骤，限制在 **1-3 步** 内。
    - **默认常规任务**：限制在 **3-5 步** 内。
    - **极致复杂任务**：最多不超过 **8 步**（除用户要求逐天极致穷尽式事实核验外）。
*   **目的**：避免无意义的步骤拆分导致智能体陷入冗长的 ReAct 循环，降低总体执行时间与 API 消耗。

### 5.2 精确度关联的无工具闭环通路 (Precision-Linked No-Tool Bypass)
*   **规范机制**：Executor 采取“分级旁路”策略，使工具调用与步骤精度强关联：
    - **低精度步骤 ($\le$ L3)**：允许 Executor 彻底旁路物理工具调用。如果 Executor 的参数化常识（LLM Parametric Knowledge）或 `<shared_memory>` 已经具备足够的可行解（例如：常规自驾路线大纲、城市间概略距离），**严禁发起任何占位或虚拟的工具调用**（如 `echo` 占位、强制写入临时文件、或冗余的 Tavily 搜索）。Executor 直接编写事实总结并收敛。
    - **高精度步骤 ($\ge$ L4)**：**强制必须调用真实工具验证数据**。Executor 严禁依靠常识或历史记忆直接闭环，必须通过物理工具（Search API、Terminal Command、Database API 等）获取时效性证据，并在输出中明文标注数据来源与时间戳。

### 5.3 内存感知优先 (Shared Memory First)
*   **规范机制**：Executor 在为当前步骤选择工具或启动查询前，**必须优先阅读并复用 `<shared_memory>` 中已沉淀的历史数据**。
*   **目的**：防止在多步骤长流程中，针对相同的地点、相同的主题重复发起完全一致的外部 Web 搜索或 API 轮询，最大化内存复用效率。

### 5.4 工作空间安全隔离协议 (Workspace Isolation & Safe Redirection)
*   **规范机制**：除代码库直接开发与系统环境维护任务（针对 `app/`, `mcp_servers/`, `docs/`, `.env` 等已知敏感代码目录的物理写操作）外，所有由任务步骤产生的数据报表、行程草稿、临时导出及分析结果，**必须严格限定在 `data/workspace/` 目录下**。
*   **物理隔离拦截器 (Workspace Path Interceptor)**：
    - 在 LangGraph 工作流的 `tool_node` 层，对所有文件操作（如 `write_file`, `read_file`）的路径参数进行物理过滤。
    - 若 Executor 试图在 `data/workspace/` 以外的地方（如根目录或自行创建的 root 临时文件夹）写入任务结果，拦截器会在底层**自动强行将其安全重定向**至 `data/workspace/`。
    - 拦截重定向后，返回给 Executor 的工具 Observation 中会追加安全提示：“*【安全提醒】由于路径合规限制，文件已自动重定向保存至 data/workspace/xxx*”，从而在底层实现完全的路径安全性，根治根目录污染问题。

### 5.5 模块化工具语义路由 (Tool RAG)
*   **规范机制**：为了防止在安装大量 MCP 服务或自定义 SKILLS 时产生 Context Window 爆炸和 Token 成本激增，Planner 不再盲目加载全量工具描述，而是执行 **Tool RAG 语义过滤与动态召回**：
    - **基础设施工具自动注入**：核心服务器（如 `system_runtime`、`web_search`）提供的读写文件、终端命令及万能搜索工具，默认 100% 注入 Planner 上下文，保障 ReAct 框架的基础物理交互能力。
    - **领域特种工具语义检索**：除基础设施工具外，其余所有领域专用工具（如 `crypto_market` 等）在加载时会自动通过 `litellm.embedding` 将其名称和描述计算为 768/3072 维度的向量，并持久化于 `mcp_tool_index` 表中。
    - **动态检索注入**：在 `Planner` 拆分步骤前，计算用户原始 Query 的 Embedding，在向量库中通过 L2/余弦距离动态召回最相关的 Top-K（默认为 3）个特种工具，并将其 Schema 注入 `PLANNER_PROMPT` 的 `<available_tools>` 中，引导 Planner 精准使用专业技能，杜绝 Executor 机械执行 `curl` 等原始命令行。

### 5.6 宏观意图精度截断 (Macro-Intent Precision Cap)
*   **规范机制**：子任务的精确度等级标定必须符合用户全局会话的“宏观意图约束”：
    - **意图分析过滤**：Planner 在进行子任务拆解前，必须对用户 Query 进行宏观语义检测。如果捕捉到诸如“简单点”、“大纲即可”、“粗略攻略”、“概算”等明显的简化指示，系统将自动激活“意图精度截断器”。
    - **上限封顶拦截**：在意图精度截断器激活状态下，Planner 产生的所有子步骤的精确度等级标签 **最高强行封顶在 L3 (FEASIBLE_PRACTICAL) 级别**。
    - **审计柔性匹配**：由此生成的子任务不仅步骤极度简练（合并在 1-3 步），且下游 Executor 和 Auditor 均遵循 L3 “实用柔性准则”，杜绝了因强行要求高精度（L4/L5）而对酒店固话、客房实时房态链接等模糊信息发起深度纠错和反复重试，实现极致的敏捷交互。
